# Findings: data logging, DAPLink and reading the log while a program runs

This document was generated by Claude in the Foundation's Claude instance. It has NOT been
reviewed by a person yet.

Written while prototyping a request/response protocol for reading the micro:bit data log
over the serial link (`source/samples/SerialBridgeTest.cpp`, and
`docs/log-over-serial-browser-client.md` for the protocol itself). Most of what follows is
incidental to that work: things that got in the way, several of which look like genuine
defects in `codal-microbit-v2`.

**Read the status label on each item.** Some are verified in source, some were observed on
hardware, and at least one is an untested hypothesis. They are not equally solid and should
not be reported upstream as though they were.

Line numbers are against `codal-microbit-v2` at `master` as checked out in
`libraries/codal-microbit-v2` during this work.

---

## 1. `MY_DATA.HTM` is not a reliable witness

**Status: verified in source, and it invalidated some of our own earlier evidence.**

The file on the `MICROBIT` drive is served by DAPLink from its flash, and the host caches
the mass-storage sectors. The drive is only remounted by `MicroBitLog::_setVisibility()`,
which returns early unless the filename, size or visibility has actually changed —
ordinary logging never triggers it.

So `xxd /Volumes/MICROBIT/MY_DATA.HTM` can return a stale copy, or a mixture of two points
in time if the OS re-reads some sectors and not others. The viewer page embedded in the
file admits this itself; its "Update data…" button is literally:

```js
update: alert.bind(n, "Unplug your micro:bit, then plug it back in and wait"),
```

**Consequence for anyone debugging the log:** dump the file only after a physical replug,
or better, ask the device instead. Our bridge grew a `D` command for exactly this — it
reports `isPresent()`, `isFull()`, `getDataLength(CSV)` and the first 64 bytes as hex, all
read live over I2C.

We lost time to this. Several dumps that looked like corruption may simply have been stale
reads, and the corruption described in section 5 is still unexplained partly because the
instrument was unreliable.

## 2. `_invalidate()` zeros 44 bytes of a 45-byte struct

**Status: verified in source. Not observed causing a failure.**

`MicroBitLog.cpp:916-921`:

```cpp
MicroBitLogMetaData m;
memclr(&m, sizeof(MicroBitLogMetaData));
flash.write(startAddress, (uint32_t *) &m, sizeof(MicroBitLogMetaData)/4);
```

`MicroBitLogMetaData` is `char[18] + char[11] + char[11] + char[5]` = **45 bytes**, not a
multiple of four. `45/4` is 11 words — 44 bytes. The last byte is left as it was.

The struct's own doc comment still reads `(40 bytes)`, which predates the addition of
`daplinkVersion[5]`. The size changed and this division was never revisited.

Small, clear, separable. Worth a PR on its own.

## 3. A data-page erase does not invalidate the cache

**Status: verified asymmetry in source. Mechanism is plausible but UNTESTED — we never got
to the experiment that would confirm or kill it.**

`MicroBitLog.cpp:766-771`, erasing the next page as the log grows into it:

```cpp
if (spaceOnPage <= l && dataEnd+spaceOnPage < logEnd)
{
    uint32_t nextPage = ((dataEnd / flash.getPageSize()) + 1) * flash.getPageSize();
    flash.erase(nextPage);
}
```

Twenty-five lines below, `:805-806`, the journal does the same thing properly:

```cpp
cache.erase(journalHead);
flash.erase(journalHead);
```

Same operation; one invalidates the cache and the other does not. After `:771` the cache
can still hold the pre-erase contents of a page that is now all `0xFF`.

Why it would matter, if it matters at all:

- `FSCache` is **write-through**, and `FSCache::write` rounds each write out to 32-bit
  boundaries, taking the padding bytes from the cached page:
  ```cpp
  alignedStart = a & 0xFFFFFFFC;
  flash.write(alignedStart, (uint32_t *)(c->page + (alignedStart % blockSize)), (alignedEnd - alignedStart)/4);
  ```
  CSV rows are not 4-byte aligned, so nearly every row write pads from the cache. A stale
  block means stale bytes written onto freshly erased flash.
- `cache.read()` of that region returns stale bytes rather than `0xFF`, which breaks
  `init()`'s walk-forward-until-`0xFF` at `:116-125` — the only way `dataEnd` is recovered
  at boot.

**Why it would normally stay hidden.** The cache is four blocks of 256 bytes
(`MicroBitLog.cpp:58`). Append-only logging has a working set of two — the current data
block and the journal block — so a block belonging to the *next* page is almost never
resident when `:771` erases it.

**What would wake it.** Random-access reads of the log, interleaved with logging. That is
exactly what a side-channel reader does, and nothing else in CODAL does it: DAPLink serves
`MY_DATA.HTM` from its own flash and never goes through this cache.

Related, same area: `FSCache::erase` only invalidates the block whose address matches
*exactly* (`getCacheEntry(address)`), but a flash page spans several 256-byte blocks. So
even the "correct" journal path at `:805` only clears the first block of its page.

**The experiment that settles it**, for whoever picks this up — same firmware, no code
change:

1. Log past a page boundary, then **while still logging** issue a dozen reads spread
   across the log, then keep logging. Dump.
2. Clear, log the same amount, **stop logging**, issue the same reads, log some more. Dump.

If 1 corrupts and 2 does not, it is reads interleaved with page erases. The proposed fix is
`cache.erase(nextPage);` before `flash.erase(nextPage);` at `:771`.

## 4. Reflashing invalidates the log, by default

**Status: verified in source.**

`MicroBitConfig.h:327-329` — `CONFIG_MICROBIT_ERASE_USER_DATA_ON_REFLASH` **defaults to 1**.
`MicroBit::eraseUserStorage()` (`model/MicroBit.cpp:474-476`) then calls `log.invalidate()`
when it detects a reflash.

Not a bug, but it has a consequence that shapes the whole side-channel design: **a user
flow cannot be "plug in, flash a reader firmware, fetch the data"**, because the flash
destroys the data. The reader has to already be part of the student's program.

We set it to `0` in `codal.json` while debugging, and it is **now back at the CODAL
default**, so reflashing clears the log again. Setting it to `0` did not stop the
corruption in section 5, which is part of why that section is still unexplained.

## 5. Unexplained metadata corruption

**Status: observed on hardware, NOT explained, and the evidence is partly suspect because
of section 1.**

Two dumps of the metadata block at offset 2048, good and bad:

```
good:   UBIT_LOG_FS_V_002\n  0x0001EFFC  0x00002000  0258  Time (seconds),temperature,light
broken: UBIT_LOG_FS_V_002\n  0x00000000  0x00000000  0258  temperature,light,Time (seconds)
```

What we established:

- **The page was genuinely erased and rewritten**, not overwritten in place. `E` (0x45)
  became `0` (0x30), and 0x30 needs bits 4 and 5 which 0x45 has clear — clearing bits
  cannot set them.
- **It is not `_invalidate()`**, which would have taken the version string with it.
- With both addresses zero, `_isPresent()` (`:976`) fails, so CODAL reformats the log on
  every boot. Observed: the log did not survive a reset.
- The flipped column order is consistent: `_endRow()` (`:560`) prepends the Time column
  only when `dataStart == dataEnd`, so `temperature,light,Time (seconds)` means the log
  believed data already existed while `headingCount` was 0.
- **But `_clear()` cannot produce those bytes.** It builds `dataStart` from compile-time
  constants at `:252-256` — 2048 + 2048 + 4096 = `0x2000`, which is exactly what the good
  dump shows. The smallest value it could ever write is `0x00000800`.

So the bytes have the shape of `_clear()`'s output but hold values `_clear()` cannot
generate. We never resolved that, and section 1 means some of the dumps behind it may not
represent any single moment in time.

A bisect over three builds (no log use / one `setTimeStamp` / the full bridge) found all
three clean at boot, and logging, reset, clear and reflash all clean. Only the full client
flow reproduced it — which is why section 3 became the lead suspect, and why the untested
experiment there is the obvious next step.

## 6. A device that only speaks when spoken to cannot be heard

**Status: observed, by us on the device side and by the client-side work on the browser
side. The underlying DAPLink behaviour has not been instrumented.**

A short, isolated reply from the nRF52 does not reach a WebUSB client. A chatty program
gets through; a request/response one does not.

Two observations, neither a full explanation: it was first described as "nothing comes out
until about a kilobyte has accumulated", and separately, measured from the client, **when
the buffer overflows the oldest bytes are discarded**.

Our workaround: the device sends about 2KB of filler and puts the real reply **last**, so
the reply is the newest thing in the buffer and cannot be the thing dropped. That works
under either explanation. An earlier attempt that sent the reply first and the filler
behind it lost the reply every time.

Two things worth saying out loud:

- **`screen` does not reproduce any of this.** It opens the CDC port, which the OS polls
  continuously, so bytes come straight out. Every message in our protocol worked perfectly
  over `screen` and then failed over WebUSB. Device-side testing over a terminal is not
  evidence about the browser path.
- **Do not work around it by reflashing.** It does clear the buffer. It also wipes the log.

This is a real constraint on *any* request/response side channel over DAPLink serial,
including the mailbox design in section 7 — "the device cannot answer until it has first
said a kilobyte of nothing" is not a tolerable contract for a product.

## 7. How this relates to issue #271 and the `codal-mailbox` branch

[lancaster-university/codal-microbit-v2#271](https://github.com/lancaster-university/codal-microbit-v2/issues/271)
— *"Design sidechannel comms approach we're happy to live with for some time (mailbox)"* —
is the long-running thread on exactly this problem. Open since Feb 2023, revived July 2025,
no decision reached.

**There is already a draft.** `origin/codal-mailbox` in this checkout, Joe Finney, April
2023. `DataLogMailboxHandler` is structurally near-identical to what we built
independently: byte-offset `GET_CSV_DATA`, fixed 128-byte blocks via
`log.readData(..., requestIndex, 128, DataFormat::CSV, maxlength)`, an interrupt-context
`process()` that defers to a fiber via an `Event`, and a `busy` flag that drops concurrent
requests. Anyone continuing this work should read it before designing more protocol.

Its `REQUEST_COLUMN_NAMES` command is marked `// TODO`, which is the same gap we hit: the
headings are private members of `MicroBitLog` (`inc/MicroBitLog.h:217-218`) with no public
accessor, so a device cannot report the columns the next row will be written against. A
small public accessor on `MicroBitLog` fixes it — a `codal-microbit-v2` change, smaller
than the `codal-core` receive filter the production version also needs.

Points from this work that are worth taking to that thread rather than filing separately:

- Section 3, if the experiment confirms it. Every design that reads the log while the
  program keeps writing to it lands on that path, the mailbox draft included. It also lines
  up with martinwork's comment there that fetching data "could be stalled by the firmware
  erasing pages".
- Section 6. It constrains any request/response side channel over serial, whatever the
  framing.
- Section 4, as the reason a "flash a reader and fetch" flow cannot be the product.
- The `H` / `REQUEST_COLUMN_NAMES` gap and the one-accessor fix.

The open question in that thread that matters most to us is jaustin's, unanswered since
July 2025: if WebUSB availability is roughly the same as Web Bluetooth, the existing
Bluetooth utility service could serve every case and the serial work is redundant. That is
a question for the team, not something to settle by building.

## 8. Measured: how fast the log can be read, and what limits it

**Status: measured on hardware, 2026-11-10, with `T` and `F` in
`source/samples/SerialBridgeTest.cpp`. Stock `CONFIG_MICROBIT_LOG_CACHE_BLOCK_SIZE` of
256. Logging stopped, 27109 bytes in the log, 64 reads per measurement.**

```
t <size> <pattern> <reads> <microseconds> <us per read> <bytes per second>

t 16  0 64   80473  1257 12724      t 16  1 64 1339172 20924   764
t 64  0 64  319416  4990 12823      t 64  1 64 2179312 34051  1879
t 128 0 64  639414  9990 12811      t 128 1 64 1959356 30614  4180
t 256 0 64 1279376 19990 12806      t 256 1 64 2539398 39678  6451

f 1000 13450 9790445 1373           (write: 1000 rows, 13450 bytes, 9.79 s)
```

### The model

Every sequential figure fits one rule: **about 20.0 ms to fetch a 256-byte cache block
from the interface chip's flash, and cache hits cost nothing.**

| read size | blocks touched | predicted | measured |
|---|---|---|---|
| 16B × 64 | 4 | 79,960 µs | 80,473 |
| 64B × 64 | 16 | 319,840 | 319,416 |
| 128B × 64 | 32 | 639,680 | 639,414 |
| 256B × 64 | 64 | 1,279,360 | 1,279,376 |

Scattered fits too: 256-byte reads at unaligned offsets always straddle two blocks, and
the measurement works out at 1.98 blocks per read.

### What follows from it

- **Chunk size does not affect throughput.** 12,724 / 12,823 / 12,811 / 12,806 bytes a
  second at 16, 64, 128 and 256 bytes. The 256-byte cache block is the real unit. So
  `BRIDGE_MAX_CHUNK` need not change, and **the mailbox draft's 128-byte blocks gain it
  nothing** over our 64.
- **Sequential access matters enormously.** Scattered reads are up to **16× slower**
  (764 B/s against 12,724 at 16 bytes). A hard constraint on any design that seeks.
- **I2C and the UART are about the same speed** — 12.8 KB/s against roughly 11.5 KB/s.
  Neither dominates. If the two legs are serialised, this bridge tops out near 6 KB/s,
  about 20 s for a full 120KB log; the mailbox, which removes only the serial leg, would
  top out near 12.8 KB/s, about 9 s. **So the mailbox is worth roughly 2×, not 10×.**
  This is the answer to "is I2C the bottleneck" from martinwork's comment on #271: it is
  *a* bottleneck, of the same size as the other one.
- **Writing is slow: 9.8 ms per row, 1.37 KB/s.** A logging program holds the I2C bus for
  about 10 ms per row, and reads queue behind it.

### The cost is latency, not bandwidth

A 256-byte read is a **single** I2C transaction — `MicroBitUSBFlashManager::read` sends
one command with no chunking. At 400 kHz, 256 bytes is roughly 7 ms of bus time. The rest
of the 20 ms is `transact()` polling an IRQ line with `fiber_sleep(1)`, up to
`MICROBIT_USB_FLASH_MAX_RX_RETRIES` (20) attempts.

The writes confirm it: a **13-byte** write costs 10 ms while a **256-byte** read costs
20 ms. Under a bandwidth limit the write would be twenty times cheaper; it is twice.

**So 12.8 KB/s is probably not a hardware ceiling.** It is what you get from fetching in
256-byte units when the per-transaction cost is largely fixed.

### Measured: a bigger cache block lifts it by about a third

`CONFIG_MICROBIT_LOG_CACHE_BLOCK_SIZE` is overridable. Raising it from the stock 256 to
1024 was measured on the same board:

```
t 16  0 64   58623   915 17467      (sequential, 1024 byte blocks)
t 64  0 64  235942  3686 17360
t 128 0 64  451777  7059 18132
t 256 0 64  955601 14931 17145

f 1000 13450 5305658 2535           (write: 1.85x faster)
```

**12.8 → 17.5 KB/s sequential, a 36% gain.** Solving the two block sizes together gives a
**fixed cost of about 7.1 ms per transaction plus about 50 µs per byte**, so the ceiling
is roughly 20 KB/s and 1024 captures most of it (2048 would give ~18.6, 4096 ~19.2).

The 7.1 ms fixed term was confirmed independently: a single 10-byte row write measured
6.7 ms (`f 1 10 6709`). Under a bandwidth limit a 13-byte write would be twenty times
cheaper than a 256-byte read; it is twice. **The cost is latency, not bandwidth.**

Writes improved 1.85× because `MicroBitLog` writes a journal entry on each cache block
boundary (`:785`), so quadrupling the block quarters the journal traffic. Scattered reads
got about 2.6× worse, since every miss now drags in 1024 bytes.

**The setting has since been reverted**, and the demo build runs on the stock 256 so it
behaves like an ordinary micro:bit. The measurement stands on its own: CODAL's default is
leaving about a third of the read throughput on the table, which is worth raising with
Lancaster. Cautions if it is ever adopted: `FSCache` holds four blocks so it costs 4× the
RAM, `MicroBitLog` uses the same constant for journal granularity (`:785`, `:811`), and at
1024 the cache block equals the flash page, which makes the missing cache invalidation in
section 3 cover a whole page rather than a quarter of one.

## 9. Two serial readers cannot coexist at all

**Status: verified in source and reproduced on hardware, 2026-11-13.**

`codal-core/source/driver-models/Serial.cpp:503`:

```cpp
int Serial::read(SerialMode mode)
{
    if(rxInUse())
        return DEVICE_SERIAL_IN_USE;    // -1011
    lockRx();
```

`read()` takes an **exclusive** RX lock. Two readers do not share the 20-byte receive ring
and race for bytes — the second is refused outright and reads nothing.

Reproduced with the simulated student program in `SerialBridgeTest.cpp` (logo touch
toggles it): over a whole session it read **zero** bytes while the bridge worked normally,
because the bridge's main loop sits inside `read(SYNC_SLEEP)` holding the lock whenever it
waits for a request — which is nearly all the time.

**This changes the argument for the `codal-core` receive filter.** The design proposal
says polling the ring from a fiber "would race with user reads and lose data in both
directions". It is worse than that: it would not race. Whichever side claims the port
first locks the other out completely. The filter is not an optimisation over polling, it
is the only mechanism that can work.

It also sharpens what co-existence means. There are two failure directions:

- the bridge holds the lock → **the student's program never receives its own serial input**
- the student's program holds it → **the bridge never receives a request and looks dead**

Neither degrades gracefully. The lock is released while the bridge is replying, so bytes
arriving during a long reply can be taken by the other reader, which is the only case that
produces the partial corruption we originally expected to see everywhere.

Worth taking to #271: it is concrete, it is a two-line citation, and it applies to any
serial-based side channel regardless of framing.

## 10. Clearing the log does not erase the old data

**Status: verified in source and reproduced on hardware, 2026-11-18.**

Reflashing marks the log empty but leaves the previous session physically in flash.
`_invalidate()` (`MicroBitLog.cpp:908`) zeroes the metadata and, unless
`CONFIG_MICROBIT_LOG_FULL_ERASE_BY_DEFAULT` is set, erases nothing:

```cpp
#if CONFIG_ENABLED(CONFIG_MICROBIT_LOG_FULL_ERASE_BY_DEFAULT)
        _clear();
#endif
```

The `_clear(false)` that follows on first use erases only as far as `dataStart` (`:280`),
so just the first data page goes. Reproduced: with a correctly cleared log reporting 21
bytes live, a dump showed `0xFF` up to `0x2bff` and then the previous session's rows
resuming at `0x2c00` — exactly a 1024-byte page boundary.

Two consequences:

- **`MY_DATA.HTM` still renders the old rows.** A user flashes a new program, opens the
  file and sees their previous data. Setting the flag to `1` fixes it and is what makes a
  MakeCode program behave the way users expect.
- **"Cleared" is not "gone".** A student's previous data stays readable to anyone who
  dumps the file or the flash. For a product used by children that is worth raising on its
  own merits, separately from anything about browsers.

**Our serial path is not affected.** `getDataLength` and `readData` only ever expose the
live range, so a client reading over serial sees the new data and cannot reach the
residue. That is a point in favour of the approach, and the opposite of what we expected.

## Note on the build, which cost us three days

Changing `codal.json` does **not** trigger a rebuild. The config reaches the compiler
through a force-included header (`CMakeLists.txt:185`) that CMake does not track as a
dependency, so no source looks stale, the link is skipped, and `MICROBIT.hex` is left
exactly as it was — while the build prints `Built target MICROBIT_hex` and appears to
succeed.

Every config finding above was delayed by this at least once. **`rm -rf build` after any
`codal.json` change, and check `ls -la MICROBIT.hex codal.json` before flashing.**
