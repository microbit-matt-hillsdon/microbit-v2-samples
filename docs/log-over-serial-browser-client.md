# Handoff: browser client for the micro:bit data log over WebUSB

This document was generated by Claude in the Foundation's Claude instance. It has NOT been reviewed by a person yet.

## The task

Write the browser client for a protocol that is already implemented and working on the
device. It should connect to a plugged-in micro:bit over WebUSB, fetch the data log, and
show it — then follow it live as new rows are written.

Build it in this order, confirming each before starting the next:

1. **Connect and say hello.** Send `?`, display the reply. Proves the round trip.
2. **Fetch the whole log.** `L` for the length, then `R` in a loop, reassemble, show a
   table.
3. **Follow it live.** `S 1`, then read the new range each time an `N` notice arrives.

Step 1 of that list is deliberately tiny. Do not skip it — it separates "WebUSB is
misconfigured" from "my parser is wrong", and those are miserable to debug together.

## Why this matters

The goal of the wider project: a user plugs in a micro:bit and sees their logged data in
a browser, without opening the `MICROBIT` drive, without unplugging and replugging to
refresh it, and without granting a second USB permission.

The design is a small request/response protocol over the serial link — the browser asks
for byte ranges of the log, the micro:bit reads them out of flash and sends them back.
**Flash is the buffer.** Serial carries only requests, byte offsets and host-paced
chunks, so nothing sent over serial has to arrive: the host can always catch up by asking
again from an offset it already holds.

### One thing this prototype cannot become

A real user arrives with data **already in the log**. Reflashing the micro:bit clears that
log — the viewer page says so itself: *"The log is cleared when you reflash your
micro:bit"*. So a product cannot work by flashing a reader firmware on demand to go and
fetch the data; the flash destroys the data it came for.

The bridge therefore has to live inside the program the student was already running, which
is the co-mingling problem that
[lancaster-university/codal-microbit-v2#271](https://github.com/lancaster-university/codal-microbit-v2/issues/271)
exists to solve, and the reason the production version needs a receive filter in
`codal-core`. This prototype sidesteps it by owning the whole program.

None of that blocks the browser client — build it against the prototype. But do not design
the user flow around "connect, flash, read".

### `screen` working is not evidence that WebUSB will work

Learn this before you spend a day on it. The micro:bit presents several USB interfaces at
once, and `screen` opens the **CDC serial port** — not WebUSB. They are two doors onto the
same room: DAPLink has one ring buffer fed by the wire from the nRF52, and both the CDC
endpoint and the WebUSB vendor commands read out of it.

With `screen` attached the OS polls the CDC endpoint continuously, so bytes come out as
soon as they arrive. **That is why everything in this document behaved perfectly over
`screen` and then failed over WebUSB.** The filler described below exists entirely because
of a condition `screen` does not reproduce.

Two consequences:

- **Never run `screen` and the browser client at the same time.** They drain the same
  buffer and steal bytes from each other, which looks exactly like frame corruption.
- **Check whether your client sets the baud rate.** `screen 115200` sets DAPLink's UART
  speed through CDC line coding. A WebUSB-only client must set it through its own vendor
  command; if it does not, DAPLink runs at whatever was set last — possibly by your
  previous `screen` session. That works on your machine and fails on a fresh one.

### Build configuration

`codal.json` sets two options that are **not** CODAL defaults:

```json
"CONFIG_MICROBIT_LOG_FULL_ERASE_BY_DEFAULT": 1,
"MICROBIT_LOG_MODE": 3
```

`MICROBIT_LOG_MODE` picks the HTML header CODAL writes at the front of the log, and `3` is
the `datatool` mode — a local addition to CODAL, not upstream. It changes nothing the
serial protocol can see; see [`datalog-datatool-header.md`](datalog-datatool-header.md),
which also explains what it would take to reach it over the wire.

Without it, reflashing only marks the log empty: `_invalidate()` zeroes the metadata
(`MicroBitLog.cpp:913`) and the following `_clear(false)` erases flash only as far as
`dataStart` (`:280`). Everything past the first data page survives, so the previous
session's rows are still physically there and `MY_DATA.HTM` still renders them — which is
not what a MakeCode program does.

With it on, `_invalidate()` calls `_clear()`, whose default argument is that same macro,
so the whole region is erased. It also makes `uBit.log.clear()` a full erase, matching
`datalogger.deleteLog()`. The cost is a pause of a few seconds on the first boot after a
flash while ~118 pages are erased one at a time.

> **Any change to `codal.json` needs `rm -rf build` before it takes effect.** The config
> reaches the compiler through a force-included header that CMake does not track as a
> dependency, so nothing recompiles, the link is skipped, and `MICROBIT.hex` is left
> untouched — while the build prints "Built target MICROBIT_hex" and looks fine. Always
> check `ls -la MICROBIT.hex codal.json` and confirm the hex is the newer one before
> flashing. This cost us most of a day, three separate times.

### The contract to code against

The device program behaves exactly like this. Nothing else.

### Framing

Every reply is a frame:

```
<RS> TYPE arg arg ...\r\n          RS = 0x1E, record separator
```

Arguments are decimal and space separated. **Anything on the wire that does not begin
with `RS` is ordinary program output** — pass it through to the console untouched and do
not try to parse it.

Requests are whole lines terminated by CR or LF. A leading `RS` on a request is accepted
but not required, so requests can be typed by hand in a terminal.

### Messages

| Request | Device sends |
|---|---|
| (boot / reset) | `<RS>! 1 0 <mode>`, then the `D` diagnostics pair — no filler, so a WebUSB client will probably miss all of it |
| `?` | 2KB of filler, **then** `<RS>! <version> <flags> <mode>` — see below |
| `? 0` | `<RS>! <version> <flags> <mode>` alone, no filler |
| `L` | `<RS>l 2 <n>` — `n` is the CSV log length in bytes |
| `R <index> <count>` | `<RS>d <index> <n> <crc>` + exactly `n` raw bytes + `<RS>e` |
| `H` | `<RS>h <hdr> <n> <crc>` + exactly `n` raw bytes + `<RS>e` — the column header row |
| `S <0\|1>` | `<RS>s <0\|1>`, and on subscribe one immediate `<RS>N …` baseline |
| unknown / unparseable / too long | `<RS>E <code>` — CODAL error codes, e.g. `-1001` |
| `M <0\|1>` | **(dev build only)** `<RS>m <0\|1>` — toggles log mirroring, see below |
| `D` | **(dev build only)** `<RS>i <present> <full> <n>` then `<RS>x <hex>` — diagnostics |
| `T [reads]` | **(dev build only)** `<RS>b …` then `<RS>t …` per measurement then `<RS>e` |
| `F <rows>` | **(dev build only)** `<RS>f <rows> <bytes> <us> <bytes/sec>` — fill the log fast |

Unprompted, while subscribed:

| | Device sends |
|---|---|
| the end of the log moved | `<RS>N <end> <hdr>` — at most once every 250ms |

Hello flags are a bitfield: `1` log present, `2` log full, `4` mirroring on,
`8` subscribed, `16` logging is running, `32` the simulated student program is
running (see below).

`<mode>` is `MICROBIT_LOG_MODE`, the CODAL build option that picks the HTML header written
at the front of the log: `0` the data.microbit.org experience, `1` the basic offline one,
`2` next gen, `3` datatool. **It says which display experience this hex was built for.**
These builds report `3`.

It is in the hello because the header itself is **unreachable over this protocol** — `R`
reads `DataFormat::CSV`, which starts below the header, so a client that never opens
`MY_DATA.HTM` has no other way to know. See
[`datalog-datatool-header.md`](datalog-datatool-header.md).

Treat it as a property of the **build**, not of the state: it is compiled in and cannot
change while the program runs. Read it once at connect. A mode the client does not
recognise should fall back to the ordinary display rather than being refused — the list
will grow.

### Reproducing the contention this design has to survive (dev build only)

**Touch the logo** to toggle a simulated student program on and off. The top right LED
lights while it runs. It is deliberately not a serial command — once it is eating bytes,
a command to stop it is exactly the sort of thing that gets eaten.

It does the two things a real user's program does on this shared port:

- **Reads from it**, as MakeCode's `serial.onDataReceived` and MicroPython's REPL both do.
- **Writes to it**, twice a second, which lands in the middle of reply frames.

**The read side does not work the way we first assumed, and the difference matters.**
`Serial::read()` takes an *exclusive* lock — `codal-core/source/driver-models/Serial.cpp:503`:

```cpp
int Serial::read(SerialMode mode)
{
    if(rxInUse())
        return DEVICE_SERIAL_IN_USE;    // -1011
    lockRx();
    ...
```

So two readers do not share the 20-byte ring and lose bytes to each other. **The second
one is refused outright and reads nothing at all.** The bridge sits inside
`read(SYNC_SLEEP)` holding that lock whenever it is waiting for a request, which is
almost always, so a user program's reader is simply locked out.

The lock is released while the bridge is busy replying, so bytes arriving during a long
reply are the ones that can actually be taken. The simulation counts both outcomes:

```
[student] eaten 3, locked out 48217
```

Lockouts mean the user's program never sees its own serial input. Eaten bytes mean the
bridge loses a request. Both are fatal to co-existence, in opposite directions.

This is why the production version needs a receive filter in `codal-core` — **not as an
optimisation over polling the ring, but because polling cannot work at all.**

**Test your client against it before calling it done** — a client that only works with
the logo off is not finished.

A second, milder source of collisions is `M 1`, which puts logged rows on the wire as
plain text. Use that to check frame separation; use the logo to check you survive losing
requests entirely.

### Why `?` sends 2KB of rubbish

DAPLink holds serial bytes from the nRF52 in a buffer shared between its CDC port and
WebUSB. **A short, isolated reply does not reach a WebUSB client.** A program that
chatters gets through; this one only speaks when spoken to, so it does not, and a client
that sent `?` and waited would conclude the device was dead. That is not a bug in the
client.

Two observations, neither of them a complete explanation:

- it was first described to us as "nothing comes out until about a kilobyte has built up";
- and separately, measured from the client: when the buffer overflows it **discards its
  oldest bytes**.

Nobody has instrumented DAPLink to confirm either. The workaround below is sound under
both, which is the main reason to trust it.

So the device fills the buffer itself. `?` sends about 2KB of filler — lines of `.`
carrying no record separator — and sends the `!` frame **last**. You are already scanning
for `<RS>` and discarding everything else, so the filler costs you nothing but time on
the wire, roughly 180ms at 115200.

Send plain `?` once at connect. Use `? 0` for every hello after that.

**The order is the whole point.** An earlier version of this firmware sent the reply first
and the filler behind it. The reply never arrived; the filler did. The filler had pushed
it out. Putting the reply last makes it the newest thing in the buffer, so it cannot be
what gets dropped, whatever the buffer's real size turns out to be.

Two things to know:

- **`BRIDGE_PRIME_BYTES` is not tuned against a measured buffer size.** In this order
  raising it is harmless, but it buys nothing past the size of the buffer. If a client
  still sees no reply, the fault is not the amount of filler.
- **Do not solve this by reflashing the device.** Reflashing pushes bytes through the
  UART and does clear the buffer, but it also **wipes the data log** — the viewer page
  says so itself. A client that reflashes to make the link work destroys the data it
  came for.

### `D` — diagnostics (dev build only)

`D` reports what the **device** believes about the log: `<RS>i <present> <full> <n>`
followed by `<RS>x <hex>`, the first 64 bytes of CSV as ASCII hex (just `<RS>x` when
the log is empty). The same pair is sent unprompted at boot, before this program has
had any chance to change the log.

It exists because **`MY_DATA.HTM` on the MICROBIT drive is not a reliable witness.**
The host caches the mass-storage sectors, and the drive is only remounted by
`MicroBitLog::_setVisibility()`, which ordinary logging never triggers — which is why
the viewer page's own "Update data…" button just says *"Unplug your micro:bit, then
plug it back in and wait"*. A dump of that file can be stale, or a mixture of two
points in time. `D` reads DAPLink's flash live over I2C, so it cannot be.

Use it rather than the file whenever you need to know the real state.

### `T` — how fast can the log be read at all (dev build only)

`T` times `MicroBitLog::readData` on the device, with no host and no serial involved.
That call is an I2C round trip to the interface chip's flash, and **every transport pays
it** — this bridge, the mailbox design in #271, Bluetooth, all of them. It is the ceiling
nothing can beat, so it is worth knowing before arguing about links.

```
T          # 64 reads per measurement
T 200      # more, for a steadier number
```

Replies, one `b` line of conditions then a `t` line per measurement, ending with `e`:

```
b <log bytes> <logging?> <reads> <minimum needed>
t <size> <pattern> <reads> <microseconds> <us per read> <bytes per second>
```

If the log is below the minimum you get `b …` then `E -1012` and nothing else. Fill it
first with `F` rather than waiting on the one-row-a-second background logger:

```
F 1000     # about 22KB, a few seconds
T          # now there is something to measure
```

`F` writes counter values, not real readings — the data is meaningless and only there to
be read back. It uses the same column names as the background logger, so it does not add
a second header row. Its reply is also a **write** benchmark, which is worth recording
alongside the read figures.

`pattern` is `0` sequential, `1` scattered. Sizes are 16, 64, 128 and 256 bytes.

**How to read it:**

- **Compare sizes.** Each read has a fixed cost (the I2C handshake) and a per-byte cost.
  If 256 bytes costs barely more than 16, the fixed cost dominates and chunks should be
  bigger — `BRIDGE_MAX_CHUNK` is currently 64, and the mailbox draft uses 128. If 256
  costs about sixteen times 16, it is raw bus speed and chunk size barely matters.
- **Compare patterns.** Sequential reads benefit from the 256-byte cache in front of the
  flash; scattered ones defeat it. The gap is what the cache is worth.
- **Compare the best number against end-to-end throughput.** Close together means I2C is
  the bottleneck and the transport choice does not affect speed. Far apart means the link
  is the bottleneck and it does.

**Stop logging first** — press B. Rows being written during a run are I2C traffic
competing with the reads. The `b` line reports whether logging was running, so a run taken
by accident is still readable.

Needs at least 2KB in the log, and the scattered numbers only mean much with several KB —
log for a few minutes first, or they all land inside the cache.

### What the demo build is logging

A faithful C++ translation of the MakeCode program a user would really write:
**accelerometer x, y and z every 100ms**, into columns named up front, with the
`Time (seconds)` column MakeCode's datalogger includes by default. So the CSV is:

```
Time (seconds),x,y,z
1.20,-16,32,-1008
1.30,-24,28,-1012
```

**The log is cleared when you reflash**, as it is with a MakeCode program. That is CODAL's
own behaviour (`CONFIG_MICROBIT_ERASE_USER_DATA_ON_REFLASH`, default 1) — see the build
configuration note above if a flash ever leaves an old log in place.

Driven entirely by the device's buttons, with an icon showing the state:

| | | |
|---|---|---|
| **A** | start logging | tick |
| **B** | stop logging | cross |
| **A+B** | stop, clear the log, reset the columns | skull |
| *log fills* | stops itself | all LEDs on |

At roughly 20 bytes a row, ten rows a second, the log fills in about **ten minutes** —
short enough to test the full case deliberately.

**The display belongs to the logging program.** The demo build shows nothing of its own on
it, because a production bridge could not take the display from the user's program either.
Read the state from the hello flags instead. (The dev build does use LEDs — a pixel per
request, a pixel while logging — which is one of several reasons it isn't the target.)

There is no command to start, stop or clear over the wire. The logging flag is read-only —
information to show the user ("this micro:bit is not recording"), not something the client
can change.
The buttons are the user's, not yours — this is deliberately shaped like the program a
real user would be running, so do not build the client around being able to drive them.

**A clear is the case most likely to break your client.** Nothing announces it. The
end of the data simply drops to zero and the next `N` notice reports the new, smaller
end. Any read already in flight can return bytes from the old log, and any offset you
were holding is now meaningless. Handle a notice whose end is *lower* than the last
one by throwing away everything you have and reading from zero, and the clear case
comes out right for free. You can trigger it by hand to test: press A and B together.

### Following a growing log

`S 1` subscribes. From then on the device sends `N <end> <hdr>` whenever the end of the
data moves, at most four times a second. **Rows are never pushed over serial.** The notice
only tells you where the data now ends; read the new range with `R` exactly as you would
any other range.

This is what makes the design robust, and it is worth understanding before writing the
client:

- Each `N` carries the **absolute** end, never a delta. A lost or stale notice is
  therefore harmless — act on the latest value and ignore the rest.
- Notices are suppressed while a read is in progress, so an `N` frame cannot land in the
  middle of a chunk's raw bytes.
- `N` also fires when the end moves **down**, which is how a cleared log or a reflashed
  board announces itself. Discard what you hold and start again.

Subscribing sends one notice immediately so you have a baseline without waiting for the
next row.

### Reading data

**The raw bytes of a chunk are not newline-terminated.** Find the end of the data from
the `n` in the `d` header, never from a newline — log data contains newlines of its own.
The `e` frame follows immediately after the last data byte.

`count` is clamped to 64 bytes per chunk, and clamped again so a read cannot run past the
end of the log. **The `d` header always describes what was actually sent, so believe the
header, not your own request.** A client that assumes it received what it asked for will
corrupt its own reassembly on the final chunk.

Read by **byte offset, never by row number**. `MicroBitLog::getNumberOfRows` rescans the
whole log from the start on every call, so row-based paging degrades quadratically over a
full download. Byte offsets stay flat.

### The CRC

`crc` in the `d` header is **CRC-16/XMODEM** over the `n` data bytes: polynomial `0x1021`,
initial value `0x0000`, no input or output reflection, no final xor. Sent as a decimal
integer.

This was hand-written rather than reusing the SDK's `crc32_compute`, specifically so the
host implementation is unambiguous. The reference implementation is `crc16()` in
`source/samples/SerialBridgeTest.cpp` — ten lines, and a direct transliteration into
JavaScript is correct.

### Known gap: `H` cannot name the current columns

**This is a firmware limitation, not a client one, but it changes what a client can
promise.**

A host that subscribes part way through a log sees only rows from the current end onward,
and a header row in the data region is indistinguishable from a data row by format alone.
`H` exists to answer "what are the columns?".

The design proposal specifies that `H` should return the columns the *next* row will be
written against, built from the headings `MicroBitLog` already holds in memory, costing no
flash reads. **That is not implementable today.** `headingCount` and `headingsChanged` are
private members of `MicroBitLog` (`inc/MicroBitLog.h:217-218`) with no public accessor;
the public API is `isPresent`, `isFull`, `setVisibility`, `clear`, `invalidate`,
`setTimeStamp`, `setSerialMirroring`, `beginRow`, `logData`, `endRow`, `logString`,
`getDataLength`, `readData`, `getNumberOfRows`, `getRows`, `init`, and nothing else.

What the prototype does instead: `H` reads the **first row** of the log and returns it.
That is correct whenever the columns never change, which covers the ordinary case.

What it gets wrong: `MicroBitLog::_endRow` writes a *fresh header row into the data
region* whenever the columns change, so a log whose columns changed part way through
contains several, and `H` will name the wrong ones for later rows. For the same reason the
`hdr` counter in both `N` and `h` is **always 0** — the device cannot currently detect a
header change to increment it.

The fix is a small public accessor on `MicroBitLog` returning the current headings. It is
a change to `codal-microbit-v2`, not `codal-core`, so it is a smaller ask than the receive
filter, but it is still a CODAL change and belongs in the same conversation with
Lancaster. Until it lands, a client reading a whole log from offset 0 sees every header
row as it goes and can track column changes itself; a client that only follows from the
live end cannot.

### Testing the framing (dev build only)

Send `M 1` to turn on log mirroring. Each logged row is then also written to the serial
port as plain text, **outside any frame**. That is what a user's own program output looks
like on this shared wire, and it is the only way to confirm a client correctly separates
frames from console text. Send `M 0` to stop.

With logging running (press A), the device writes an accelerometer row ten times a
second, so the number returned by `L` grows visibly while you watch — and moving the
board changes the values, which makes it obvious whether a live view is really live.

### What the device does not do

The device only has to describe what it sent accurately. These are the **client's** job:

- Re-issue `R` from the last good offset when a CRC does not match, when offsets skip, or
  when `<DAPLink:Overflow>` appears in the stream.
- Detect a reset: if the length goes *down*, or a re-read of early bytes does not match
  what you hold, the log was cleared or the board reflashed. Discard and start again.
- Ask for at most one window at a time and wait for `e` before issuing the next `R`.
- Act only on the most recent `N`, and ignore older ones.

The centre LED (2,2) lights for 50ms on each **completed request line**. This is a
diagnostic, and worth using while debugging the browser side:

- **Pixel lights, no text arrives** → the browser's write path works, its read path does not.
- **No pixel at all** → the browser's write path is not reaching the device, or it is not
  terminating requests with CR or LF.

Line settings are CODAL's defaults: **115200 baud, 8N1**.

## The hardware path, and why WebUSB

Worth understanding before writing any code, because it explains the transport choice.

The micro:bit has two chips. The nRF52833 is the one you program. A second interface
chip by the USB socket runs **DAPLink**. The nRF52's own USB peripheral exists in silicon
but is **not wired to the USB socket** — the socket belongs to the interface chip. So
every byte between the nRF52 and the host goes:

```
nRF52  ──serial wire──►  DAPLink  ──USB──►  host
```

Verified in this repo: `libraries/codal-microbit-v2/model/MicroBit.cpp:73` builds
`uBit.serial` on `io.usbTx` / `io.usbRx`, two dedicated pins going to the interface chip.
There is no bypass over USB.

DAPLink does not parse these bytes and does not need to, which is why none of this work
requires a DAPLink firmware update. It is not quite a *dumb* relay, though: it buffers,
and how it buffers is the single most awkward thing about this design — see the filler
section above.

### Use WebUSB, not Web Serial

Two reasons, both of which bit the design when considered:

1. **No second permission prompt.** The coding environments already hold a WebUSB
   connection to DAPLink's CMSIS-DAP endpoint. A Web Serial connection needs its own
   permission picker, which cannot be pre-granted from the WebUSB grant.
2. **They collide.** DAPLink's CDC serial port drains the *same* ring buffer that the
   WebUSB vendor read command drains. An editor holding a WebUSB connection while a page
   holds a Web Serial one would split the bytes between the two.

Pick one pipe. It should be WebUSB.

## How to do it

**Strong recommendation: build on `microbit-connection` rather than hand-rolling WebUSB.**

Per the design proposal this task came from, `microbit-connection` already drives
DAPLink's UART at `packages/microbit-connection/src/usb/daplink.ts`, using vendor
commands `0x83` (read serial, up to 62 bytes per call) and `0x84` (write serial).

> Not verified first-hand: that repository was not available in the session this document
> was written in. Treat the file path and the command numbers as a starting point to
> confirm, not as checked fact. The existence of the WebUSB UART path is well established;
> the specifics should be read from the source.

Hand-rolling WebUSB means debugging USB interface claiming and the CMSIS-DAP handshake
instead of debugging the thing we actually want to learn about. Avoid it.

MakeCode does not use `microbit-connection` and has its own equivalent path. If this
needs to work in both eventually, keep the browser-side logic in a small dependency-free
module so it can be lifted across.

## Acceptance

Done when a page can:

1. Prompt for and connect to a micro:bit over WebUSB, and show the `!` hello reply.
2. Fetch the whole log — `L`, then `R` in a loop — verifying each chunk's CRC and
   retrying from the last good offset on a mismatch, and render it as a table.
3. Subscribe with `S 1` and append new rows as `N` notices arrive, without re-fetching
   what it already holds.
4. Notice a cleared log or a reflashed board and start again cleanly.
5. Pass non-frame traffic through to a console view rather than trying to parse it.
   Test this with `M 1`.

## Out of scope

Explicitly **not** part of this task:

- **Any firmware change.** The device side is done. If something seems to need a CODAL
  change, say so rather than making one — see the known gap on `H` above, which is
  exactly such a case and is already recorded.
- **Clearing the log from the browser.** Easy to add on the device, but a page that can
  wipe a user's data needs a confirmation story first. Deliberately left out.
- **Changing the baud rate.** It is set by the program on the device, not negotiated.
  Both sides default to 115200.
- **MakeCode integration**, and the shared client interface over Bluetooth. Both are
  later work; just keep the parser free of `microbit-connection` specifics so it can move.

## Gotchas

- **The receive buffer is 20 bytes.** `CODAL_SERIAL_DEFAULT_BUFFER_SIZE` at
  `libraries/codal-core/inc/driver-models/Serial.h:33`. The device drains it a character
  at a time and reassembles the line, so a request longer than 20 bytes is fine *provided
  the host does not outrun the device*. Requests are short (`R 65536 64` is 10 bytes), so
  this is not a practical limit — but do not batch several requests into one write, and do
  not send the next request before the previous reply has finished.

  This buffer is shared with anything else reading serial, which is why the production
  version needs a receive filter in `codal-core`. Not a problem to solve here: in the
  prototype our program owns the port.

- **Request lines are capped at 32 bytes** by the device
  (`BRIDGE_MAX_REQUEST`). Longer lines get `E -1001`.

- **`R` distinguishes its two failures.** `E -1001` (`DEVICE_INVALID_PARAMETER`) means the
  request was malformed. `E -1012` (`DEVICE_NO_DATA`) means there is nothing to read —
  either the log is empty or the offset is past the end. `H` uses the same convention.
  Call `L` first and do not read when the length is 0.

- **The centre LED no longer throttles requests.** It used to be held lit for 50ms inside
  the request loop, capping the protocol at 20 requests a second — about 1.3 KB/s at 64
  bytes a chunk, whatever the baud rate. It now blinks from its own fiber and the request
  path does not wait for it. Any throughput figure measured before this change is
  meaningless; re-measure. Requests arriving faster than the blink are simply not shown.

- **DAPLink drops bytes when overwhelmed**, and writes the literal text
  `<DAPLink:Overflow>` into the stream when it does. Unlikely at this tiny scale, but if
  you see it, that is what it is.

- **Polling cadence.** The proposal notes `microbit-connection` sleeps on a timer between
  vendor reads, and Chrome clamps nested timers to 4ms, capping throughput. Reading again
  immediately when a read returns data, and only sleeping when it returns empty, is a
  worthwhile separate improvement that needs no firmware change. Out of scope here, but
  do not be surprised by latency.

- **Baud rate is set by the program on the device**, not negotiated. Both sides default
  to 115200. Do not change it.
