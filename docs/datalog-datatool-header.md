# The `datatool` log header: a display mode carried by the hex

This document was generated by Claude in the Foundation's Claude instance. It has NOT been
reviewed by a person yet.

## What this is

A fourth `MICROBIT_LOG_MODE` in CODAL, `datatool`, so that **the same `DataLogDemo.cpp`
can be built into hexes that ask to be displayed differently**. The program is unchanged
and logs exactly what it logged before; only the HTML header CODAL writes at the front of
the log changes.

This replaces an earlier attempt at putting display metadata in the log data itself. We
are not yet sure what metadata we want, and the mode is enough to say "show this one
differently" without committing to a schema.

It follows the pattern of the existing next gen mode —
[`nextgen-header.html`][nextgen] — with `nextgen` swapped for `datatool`.

[nextgen]: https://github.com/microbit-matt-hillsdon/codal-microbit-v2/blob/next-gen/resources/logfs/nextgen-header.html

## How the mechanism works

The first 2048 bytes of the log region in flash are a minified HTML page. Everything after
it is the raw log. Together they are the file that appears as `MY_DATA.HTM` on the
`MICROBIT` drive — opening it runs the header, which finds the data below itself and
renders it.

That header is a byte array compiled into CODAL, and `MICROBIT_LOG_MODE` picks which one:

```
resources/logfs/<mode>-header.html      the source
    ↓  npm run build   (minify, pad to 2048, end with <!--FS_START)
source/MicroBitLog.cpp                  const uint8_t MicroBitLog::header[2048]
    ↓  #if (MICROBIT_LOG_MODE == n)
the hex                                 written to flash by MicroBitLog::_clear
```

The modes, after this change:

| `MICROBIT_LOG_MODE` | Header | Experience |
|---|---|---|
| 0 (default) | `default-header.html` | data.microbit.org data logging |
| 1 | `basic-header.html` | Basic offline table, `dl.js` on microbit.org |
| 2 | `nextgen-header.html` | "micro:bit — the next gen" playground survey |
| **3** | **`datatool-header.html`** | **Data tool** |

Like next gen, the header is a thin bootstrap. It sets a mode and loads
`https://data.microbit.org/v3/dl.js`, which decides what to draw:

```js
w.dl = {
  mode: "datatool",
  load: function () {},
  handleBootstrapError: function () { /* ... */ },
};
```

**The mode string is the whole signal.** It sits in the first 2048 bytes of `MY_DATA.HTM`,
so anything reading that file can find it.

## What the app side should do

There are two routes, depending on how the app reaches the micro:bit.

### Over serial

**The hello reply carries the mode as a third number.** `?`, `? 0` and the unprompted boot
hello all reply:

```
<RS>! <version> <flags> <mode>
```

so a datatool build answers `! 1 0 3`. Read it once at connect — it is compiled in and
cannot change while the program runs. See
[the protocol doc](log-over-serial-browser-client.md).

The header bytes themselves are still unreachable over serial: `R` reads
`DataFormat::CSV`, which starts **below** the header. If an app ever needs the header and
not just the mode number, `MicroBitLog::readData` already takes a format and
`DataFormat::HTMLHeader` (0) returns the header alone — `R` would need the format argument
that the Bluetooth `requestTypeLogRead` already has. Not done, and not needed for the
mode.

### From the file

Read the first 2048 bytes of `MY_DATA.HTM` and look for the mode in the bootstrap object.
After minification it appears exactly as `w.dl={mode:"datatool",`, with no spaces.

### Either way

A log with no recognised mode is an ordinary log. Fall back to the normal display rather
than refusing it — the list of modes will grow.

### The hosted `dl.js` has to learn the mode

`data.microbit.org/v3/dl.js` decides what each mode renders. Until it recognises
`datatool`, opening `MY_DATA.HTM` will do whatever it does with an unknown mode — most
likely nothing useful. That is a change on the web side, not in the hex.

To try a header locally before then, point `<base>` and the script `src` at a local copy
of `dl.js`. `npm run test` in `resources/logfs` does something similar for the basic mode.

## The CODAL change

Four files, in `codal-microbit-v2`:

| File | Change |
|---|---|
| `resources/logfs/datatool-header.html` | New. `nextgen-header.html` with `mode: "datatool"`. |
| `resources/logfs/build.js` | `datatool` added to the list of modes to generate. |
| `source/MicroBitLog.cpp` | New `#elif (MICROBIT_LOG_MODE == 3)` branch holding the generated 2048-byte array. |
| `inc/MicroBitConfig.h` | Mode 3 documented alongside the other three. |
| `resources/logfs/README.md` | "three header formats" → "four". |

The byte array was generated by CODAL's own tooling, not by hand:

```bash
cd resources/logfs
npm install      # once
npm run build    # rewrites the arrays in source/MicroBitLog.cpp
```

It reported **1384 bytes spare** of the 2048 for the datatool header, and regenerated the
other three byte-for-byte identically. Re-run it after any edit to the HTML; the build
fails rather than truncating if a header will not fit.

### Where the change currently lives

`libraries/codal-microbit-v2` in this repo is a symlink to `~/Code/codal-microbit-v2`,
which is a plain checkout of `lancaster-university/codal-microbit-v2` **on `master`**. So:

- The change is not tracked by this repo, and `codal.json` still points at upstream
  `master`.
- Anyone else building this hex gets mode 3 undefined and `#error` from `MicroBitLog.cpp`.

To make it reproducible it needs a branch of `codal-microbit-v2` — as next gen has — with
`codal.json` here pointed at it:

```json
"target": {
    "name": "codal-microbit-v2",
    "url": "https://github.com/microbit-foundation/codal-microbit-v2",
    "branch": "datatool-header",
    "type": "git"
}
```

Until then it only builds on a machine where that checkout carries the change.

## Building the hex

`codal.json` in this repo now selects the mode:

```json
"config": {
    "CONFIG_MICROBIT_LOG_FULL_ERASE_BY_DEFAULT": 1,
    "MICROBIT_LOG_MODE": 3
}
```

```bash
rm -rf build          # required: see below
python3 build.py
# drag MICROBIT.hex onto the MICROBIT drive
```

> **`rm -rf build` is not optional here.** A `codal.json` change reaches the compiler
> through a force-included header that CMake does not track as a dependency, so nothing
> recompiles, the link is skipped and `MICROBIT.hex` is left untouched — while the build
> prints "Built target MICROBIT_hex" and looks fine. Check `ls -la MICROBIT.hex
> codal.json` and confirm the hex is newer before flashing. This has cost us a day,
> three times.

Confirm it worked by opening `MY_DATA.HTM` on the drive in a text editor and looking for
`datatool` near the top. If the old header is still there, the hex did not rebuild.

The header is written to flash by `MicroBitLog::_clear` (`MicroBitLog.cpp:285`), which runs
on reflash, so it updates with the hex.

> Not compiled or flashed. The ARM toolchain is not available in the session this was
> written in, so the C++ change has not been built and the hex has not been produced. The
> header generation *was* run, and the 2048-byte array verified to decode back to valid
> HTML carrying `mode:"datatool"`.

## What the program logs

Unchanged. `source/samples/DataLogDemo.cpp` as it was: accelerometer x, y and z every
100ms, A to start, B to stop, A+B to clear, the same serial protocol. See
[the handoff doc](log-over-serial-browser-client.md).
